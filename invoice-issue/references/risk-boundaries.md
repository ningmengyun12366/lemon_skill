# 发票开具风险边界

本文件定义发票开具的风险边界、重复开票拦截、敏感信息边界和包体边界。命中风险边界时，停止自动推进并按 [error-handling.md](error-handling.md) 输出。

## 正常路线边界

- 正常路线必须是：预检、`invoices[]` 检查、预览 Markdown 原样展示、用户明确确认、`issue-from-output --confirm-preview --pretty`、读取并交付最终结果。
- 正式开票只使用上述命令，不自行构造 HTTP 请求。
- 不绕过 `issue-batch-invoice-info-check`、预览确认、权限认证或结果轮询。
- 不根据任务状态 JSON 自行改正式 payload。
- 不为了让校验通过而补造销售方、购方、商品、金额、税率、证件号或税号。

## 误开票拦截

以下情况必须阻断或转人工：

- 没有真实交易依据仍要求开票。
- 要求把购方改成与真实交易不一致的公司或个人。
- 要求把商品/服务名称改成与真实交易不一致的内容。
- 要求虚增、虚减、拆改金额以规避规则。
- 要求选择无依据低税率、免税或不征税。
- 企业名称和统一社会信用代码明显不匹配。
- 增值税专用发票缺少购方名称或购方税号。
- 商品编码低置信且税率差异明显。
- 金额、税额、价税合计关系不一致。
- 后端返回风险阻断或人工审核。

含税金额很小导致按税率计算或四舍五入后的明细税额、合计税额为 0，不属于金额关系不一致；不得仅因税额为 0 阻断草稿或预览。

建议话术：

```text
这个请求可能导致发票内容与真实交易不一致，我不能继续自动开具。可以按真实交易信息重新生成草稿，或转人工审核处理。
```

## 自然人与企业边界

- AI/Agent 必须先判断购方是自然人还是企业/单位，并把判断写入 `purchaserInfo.isNaturePerson`；不依靠名称猜测来覆盖用户已明确的购方类型。
- 普通发票给自然人开具时，身份证号和证件号不是默认必填项。
- 用户明确“不提供身份证号/证件号”且当前是普通发票自然人购方时，应继续草稿检查，而不是反复追问。
- 自然人购方不得调用企业搜索。
- 自然人姓名即使命中企业候选，也不能要求用户选择企业。
- 不能伪造自然人证件类型、证件号码或税号。
- 只有后端检查、地区规则或票种规则明确阻断时，才追问自然人证件信息。
- 企业搜索仅作参考；企业普通发票搜索不到税号、接口失败/超时或用户不选择候选时，可继续生成不带购方税号的草稿和预览，不阻止草稿。
- 企业增值税专用发票缺少购方税号时必须阻断。

## 重复开票

命令提示同内容重复开票时停止并向用户说明风险。5 分钟内的重复检查覆盖处理中、已提交、结果未知或已完成任务；超过窗口也不能把已有任务重复提交。

不能通过改任务文件名、路径、时间戳或收票联系方式，把同一笔业务当作不同开票请求。

同内容重复任务按状态处理：

- 5 分钟窗口内存在同发票内容任务（未完成、处理中、已提交但无终态、提交超时、结果未知或已完成）时，默认阻断再次正式提交并提示重复开票风险。
- 用户明确二次确认仍要重复开票后，才允许追加 `--confirm-duplicate` 重新执行正式提交；超过 5 分钟后不再因历史同内容任务阻断。
- 用户说“再开一张一样的”但没有合法重开依据，或只改收票邮箱、手机号等非交易实质字段后要求再开，仍应阻断。
- 后端返回 `duplicate_blocked` 时阻断。
- 当前任务状态已经记录 `taskID` 时，只能查询该任务结果，不得再次正式提交。

## 纳税人身份与销方资料

- 开票纳税人身份只取任务 `enterprise_context.nsrzg`：`0` 为一般纳税人，`1` 为小规模纳税人；禁止使用工作区或历史企业状态兜底。
- `nsrzg` 缺失或非法时，合法人工 `taxpayerType` 可作为人工确认；否则提示 `taxpayer_identity_missing`，保留用户显式票种/税率并跳过依赖身份的自动判断。
- 开票资料检查只使用本次任务企业信息；独立画像查询结果不能代替开票企业信息。
- 销方地址、电话、开户银行和银行账号均可选，有值传、无值省略；销方名称以用户输入优先，否则只取任务 `enterprise_context.enterpriseName`。

允许的替代路径：

- 查看或重发原发票。
- 合法作废后重开。
- 合法红冲后重开。
- 合并开票，但必须列明多个订单。
- 拆分开票，但必须明确拆分金额和业务依据。

## 提交结果未知或权限恢复

- 已有 `taskID` 时使用原任务查询结果；不能另建任务再次正式提交。
- 旧任务明确返回 `code=2015`、`data.status=-1`，且 `issue_completed=false`、没有已开票产物、当前权限认证已通过时，可按命令提示复用原任务恢复一次。
- 权限恢复不使用 `--confirm-duplicate`，不得手工修改任务号、提交状态或确认状态。
- 命令返回结果未知、恢复失败或无可查询任务号时停止自动提交，先请用户核实税局或平台记录。
- 接口超时、DNS 异常、网络断开或 stdout 截断不能作为重新开票的依据；可续查时查询原任务，否则停止。

## API Key 与权限边界

- API Key 不写入 Skill 包、参考文档、runtime-config、日志或 evidence。
- API Key 应通过本地安全配置和 `workspace-config-writer` 写入。
- 本地配置已有 API Key 时，预检命中 `apikey_confirmation_required` 必须先询问用户是否沿用；用户确认前不得继续调用远程业务。
- 工作区配置不保存销售方 `uscc` 或 `companyInfo`。新任务必须显式提供销售方税号，任务续跑只能使用已固化的 `enterprise_context`。
- “无权调用该能力”表示 API Key 未绑定发票开具能力或对应企业；不能解释成税局登录失败。
- `40001 请求校验失败` 不能直接解释成 API Key 未绑定企业；应先检查 CLI、API Key 是否写入、销售方企业、workspace 配置和 `invoices[]` 请求体。
- 不要求用户在公开聊天中反复粘贴 API Key；如需配置，指导其使用本地配置命令。

## 税局认证与敏感输出

- 不索取税局密码、短信验证码、二维码截图、人脸信息或身份证照片。
- 不引导绕过登录、人脸认证、企业授权或税局风控。
- 登录失效时必须将命令返回的安全登录链接或认证 Markdown 按原始裸文本完整展示；不得省略链接，也不得自行拼接或猜测地址。
- 人脸认证失效时只展示 CLI 本地生成的白底二维码 PNG/认证 Markdown；二维码按 5 分钟失效处理，不展示二维码原文、Base64、`rzid` 或内部认证编号，也不得把图片内容交给第三方二维码服务。
- 认证未通过前不得正式提交。
- 不主动展示任务状态 JSON 路径、预览文件路径、正式 payload、内部字段名或命令行细节。
- 必须原样展示二进制生成的预检、预览、认证和结果 Markdown；不摘要、不重排、不改写。

## Windows 和编码边界

- Windows 中文 JSON 输入优先使用 UTF-8 文件和 `--input`。
- PowerShell 里避免复杂 here-string 和 stdin 管道 JSON。
- 乱码优先按终端显示编码或读取编码排查，不直接认定 JSON 损坏。
- `Unexpected UTF-8 BOM` 按编码兼容问题处理，重写为 UTF-8 无 BOM 或使用兼容读取。

## 包体边界

- ZIP 包保持轻量，只包含 skill 文档、runtime、assets、参考文档等发布所需文件。
- 不把 `bin/**` 放进 ZIP。
- 不把 `scripts/**` 放进 ZIP。
- 平台二进制通过安装文档中的当前平台下载表外置下载。
- 不能从 qclaw offline 包复制离线胖包结构到当前 skill。
